## 2. Make assessment and audio work together by design

1. **Define the skill map.** Begin with number recognition, tens and ones, addition without carrying, subtraction with borrowing, halves and quarters, initial sounds, word decoding and short-sentence reading. Give each a stable ID, prerequisites, level descriptors, common errors and at least two teaching activities. Have educators approve the graph and mastery rubric before using them for recommendations.
2. **Define a question item.** Store skill, item or template ID, version, difficulty band, language, prompt, stimulus, expected response, scoring guidance and permitted audio. Numeracy generators produce valid operands and compute the answer. Literacy reviewers author sounds, words and passages separately for each language and script. Record the assessment language with the observation so that comprehension in one language is interpreted correctly at the destination.
3. **Generate each session dynamically.** Select the next skill and difficulty from the learner's recorded evidence, then construct a fresh eligible question from approved generation rules or select an unseen language-specific item. Numeracy varies operands, representations and task formats within the target skill. Literacy selects reviewed words, sounds and passages at the appropriate language-specific level. Store the actual question and presentation order before display. A resumed session restores that same question. Track previous exposure across sessions so changing the session ID does not reset repeat protection. Offline packs contain a bounded set of valid, voiced variants. If the eligible material is exhausted, explain the choice to repeat, change level or stop.
4. **Adapt to evidence.** As an initial rule for educators to pilot, a successful independent response offers a harder item and a supported response offers another example or a prerequisite check. Record independent, prompted, incorrect and skipped observations separately. Require the teacher to confirm the final status against the rubric. A single answer, skip or audio failure cannot silently assign mastery.
5. **Specify what the learner may hear.** Audio can present an oral task or an instruction. For a reading test, hearing the target word can reveal the answer. Store the spoken instruction separately from the reading stimulus, and record assisted attempts if the teacher supplies the answer. Test this distinction in every language.
6. **Define the receiving plan.** Choose the first unmet prerequisite, with an educator-approved tie rule across strands. Show the observation supporting the suggestion, one peer-group recommendation and two concrete 15-minute activities. Define empty, all-mastered and insufficient-evidence states. Changing the interface language only changes the presentation.
7. **Set the audio catalog size from real content.** Count the distinct approved spoken strings per language, including variable questions and activities. Deduplicate identical recordings by exact text, language, voice, model and settings. Variable questions make a fixed clip count unreliable. Estimate generation cost and phone storage using a measured sample before committing to the full pack.

## 3. Establish the technical contracts

### Assessment engine specification

The assessment must choose questions from the learner's responses and prior evidence. Each skill has multiple question families and difficulty bands. A teacher can request an alternative, and reassessment uses fresh eligible material. A shared script for every learner would fail the acceptance tests below.

| Engine component | Required behavior |
| --- | --- |
| Starting point | Use the learner's earlier evidence where available. For a new learner, use a short educator-approved entry check. Age can suggest an entry band, while demonstrated skill determines the follow-up. |
| Question construction | Constrain generated arithmetic to the intended skill and compute its expected answer independently. Vary task formats as well as numbers. For literacy, combine reviewed language-specific stimuli with approved task instructions and difficulty tags. Store a canonical identity for equivalent questions so cosmetic wording changes cannot bypass repeat protection. |
| Follow-up selection | An independent success offers a harder or transfer task. Difficulty offers another format at that level or an unmet prerequisite. A skip leaves ability undecided and offers an alternative or a pause. Pilot these rules with teachers and version them with the rubric. |
| Evidence and scoring | Keep the presented item, response or structured teacher observation, assistance level and rubric version together. Score structured numeracy responses against the computed answer. Teachers judge oral and reading performance against reviewed rubrics. Record teacher overrides with a reason and preserve the original evidence. |
| Completion | Educators define the minimum evidence, time/item limits and stopping rules before the pilot. Stop when the skill has sufficient evidence, the learner pauses, or a limit is reached. Show insufficient evidence when needed. A timeout cannot count as failure. |
| Teacher controls | Allow pause/resume, alternate question, skip and review. Asking for an alternative before an answer does not count as an incorrect attempt. Keep the teacher's assessment language independent of the interface language. |
| Content quality | Publish only questions passing arithmetic, difficulty, answer and language checks. Teacher-authored additions use the same review and versioning process. Runtime generation uses approved constraints. Treat any future AI-authored content as a draft requiring validation before publication. |
| Audio availability | Build voiced variants from the same versioned generator rules and approved scripts used by the assessment. In an installed audio pack, select an eligible item with its exact approved recording. Offer text or available device speech for uncovered items, with a visible availability state. Newly generated speech requires a connection and a completed provider request before it can be cached. |

For example, one learner may independently solve an addition item and receive a harder representation. Another learner who needs prompting receives a place-value check. A returning learner receives an unseen eligible variant. Persist the selection reason so a teacher can understand the session and the team can reproduce it during debugging.

**Offline scope:** a downloaded pack has finite content and recordings. Set its question-family coverage, variants per difficulty, repeat policy and storage budget explicitly. Full offline voice coverage means every item the installed pack may present has the matching reviewed recording. Record coverage per language in the release evidence.

The following stack is a proposed implementation choice for this plan. Lock supported versions at kickoff and record the account-specific service decisions.

| Area | Proposed design and contract |
| --- | --- |
| Mobile web app | React, TypeScript and Vite PWA. IndexedDB stores scoped rosters, drafts, completed sessions and pending events. A service worker caches the app shell and installed content. The first online setup provisions the device and downloads selected packs. |
| Session and evidence | A learner has a random pseudonymous ID. A session stores an immutable content version, assessment language, attempts and teacher-confirmed statuses. Committing an answer and advancing the cursor is one local transaction. Each reassessment creates a new session linked to its predecessor. |
| Transfer | Define a bounded, versioned envelope with a transfer ID, learner pseudonym, agreed age field, origin language, assessment date, content version and ordered skill summary. Share only the approved summary and evidence indicators. Test actual QR size, scan distance and print contrast on target phones. A QR or text code can be copied and read by whoever holds it. |
| Issuer trust | For school-authenticated records, an authenticated teacher requests a signature from the school’s server. Keep the private key server-side and provision trusted public keys for offline verification. A newly created offline transfer may travel immediately with its issuer labeled unverified. Later issuance creates a separate signed record. Define key expiry, rotation, revocation freshness and unknown-key behavior. Any requirement for verified issuance while disconnected needs a separate school-approved device credential design at kickoff. |
| Cloud services | Proposed AWS services are Cognito for staff sign-in, API Gateway and Lambda for authenticated operations, DynamoDB for records and aggregates, and restricted object storage for content artifacts. Enforce tenant and role permissions on the server. Publish the PWA over HTTPS, with separate Cloudflare Pages staging and production deployments. Keep runtime secrets out of browser assets. |
| Sync and analytics | Give each operation a unique ID. In one durable transaction, accept an event once and update the relevant aggregates. Acknowledge individual IDs. Remove only acknowledged events locally. Conflicting edits remain visible for resolution. Reads of aggregate statistics use bounded queries and return an as-of time. Apply school-approved suppression rules for small cohorts. |
| Audio publishing | An account-authorized build job sends approved instructional text to ElevenLabs. Publish versioned MP3s and a manifest with exact content IDs, hashes, sizes and review status. The phone verifies a whole pack before activating it and keeps its previous working pack during interrupted updates. Keep learner data out of speech requests. |

**Interfaces to agree before parallel development:** content schema and sample packs, mastery and plan functions, draft/session storage and migrations, capsule encode/decode examples, trust states, audio manifest, authenticated event submission and acknowledgement, signing endpoint, and aggregate read response. Include a successful example and a failure example for each. Freeze compatible examples as automated fixtures.

## 5. Verify the system as teachers will use it

| Test | What must happen |
| --- | --- |
| New assessment vs reassessment | Start with two synthetic learner IDs and different strengths. Generate and answer different items. Reassess one learner. History preserves the first session and the destination plan reflects the selected session. |
| Dynamic assessment | Feed the engine independent success, prompted success, incorrect and skipped responses. Verify follow-ups against the approved policy. Generate variants across every supported skill and difficulty band and check validity and expected answers. Repeated sessions honor exposure history. Save/reload preserves the current question. |
| Question and voice agreement | For every offline audio-enabled item, match the exact spoken instruction to its language, content version and question parameters. Reading stimuli remain hidden from answer-revealing audio under the approved rubric. Simulate pack exhaustion and a missing clip. The teacher can recover without losing observations. |
| Language coverage | Automatically check completeness across all seven packs and all 49 origin/interface combinations for stable skill IDs and status mapping. Human reviewers cover each script and pronunciation, with at least one receiving-teacher walkthrough per language. |

Open it on B, play the correct origin-language prompt, read the localized plan, then reconnect. Verify the intended sync is acknowledged once. |
| Failure and recovery | Deny camera access, paste a damaged code, interrupt an audio download, fill local storage, switch accounts, expire a login and repeat a sync. Each path preserves existing work where storage permits and gives the teacher a specific recovery action. |

## 6. Decide when to deploy

**Deployment-ready** means an exact candidate passed CI, the staging pilot, content and audio review, authorization checks, backup restore and rollback rehearsal. The release record identifies the commit, artifacts, configuration, migrations, device results and unresolved issues. Sai signs the teacher experience and Omkar signs technical readiness.

**Production launch** means the team has promoted those artifacts, checked the live HTTPS URL, camera access, offline reopen, audio, transfer, dashboard and sync, and recorded the result. If a release loses assessments, exposes another school's data, breaks offline transfers or misstates learning results, stop the rollout and use the rehearsed recovery procedure. Roll back the affected app, pack or backend independently where compatible. Preserve unsynced learner work and use a forward data fix when a schema downgrade would destroy records.

**After launch**, assign an owner for support, content corrections, account access, audio spend, dependency updates and restore drills. Review pilot feedback with teachers. Record which devices, languages and use cases the team has actually verified.
